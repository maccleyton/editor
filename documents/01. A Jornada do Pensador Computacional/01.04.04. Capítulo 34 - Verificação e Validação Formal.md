## 34.1 Lógica Formal em Programação

---

## 34.1.1 Lógica de Hoare

- Linguagem formal para especificar e verificar corretude de programas.
- Baseada em **tripletas de Hoare**: $\{P\} C \{Q\}$, onde:
    - $P$ é a pré-condição — condição que deve ser verdadeira antes da execução do comando $C$.
    - $C$ é o comando/programa a ser executado.
    - $Q$ é a pós-condição — condição que deve ser verdadeira após a execução de $C$, assumindo $P$ verdadeira inicialmente.
- Utilizada para garantir que um programa modifique estados conforme esperado.

---

### 34.1.2 Weakest Precondition (Pré-condição mais fraca)

- A **pré-condição mais fraca** para um comando $C$ e uma pós-condição $Q$ é a condição mais geral $P$ tal que $\{P\} C \{Q\}$ seja verdadeira.
- Permite determinar quais condições devem ser satisfatórias antes da execução para garantir que o resultado esteja dentro da pós-condição.

---

### 34.1.3 Strongest Postcondition (Pós-condição mais forte)

- A **pós-condição mais forte** para uma pré-condição $P$ e um comando $C$ é a condição mais específica $Q$ garantida após a execução de $C$, assumindo que $P$ seja verdadeira antes.
- Complementa análise formal da execução.

---

### 34.1.4 Loop Invariants (Invariantes de Laço)

- Condições que permanecem verdadeiras antes e depois de cada iteração de um laço.
- Fundamentais para provar corretude e terminação de loops.
- Exemplo de invariante: soma dos elementos processados até o momento em um laço que soma elementos de um vetor.

---

### Exemplo Guiado: Verificação de um loop de soma de vetor usando invariante

```python
def soma(vetor):
    soma_parcial = 0
    i = 0
    *# Invariante: soma_parcial = sum(vetor[0:i])*
    while i < len(vetor):
        soma_parcial += vetor[i]
        i += 1
    return soma_parcial
```

- **Invariante:** Antes e depois de cada iteração, `soma_parcial` contém a soma dos primeiros `i` elementos.
- Serve para garantir que ao final do loop, soma_parcial será soma total.

## 34.2 Model Checking

---

### 34.2.1 Finite State Machines (Máquinas de Estados Finitos)

- Modelo matemático representando sistemas através de estados e transições.
- Cada estado descreve uma configuração possível do sistema.
- Transições definem mudanças de estado baseadas em eventos.
- Usado para modelar hardware, protocolos e software de tempo real.

---

### 34.2.2 Temporal Logic (Lógica Temporal)

- Linguagem formal para expressar propriedades que variam ao longo do tempo.
- Exemplos: LTL (Linear Temporal Logic), CTL (Computational Tree Logic).
- Permite especificar requisitos como "algo sempre acontecerá" ou "eventualmente algo acontecerá".
- Fundamental para especificar propriedades em sistemas reativos e concorrentes.

---

### 34.2.3 Verificação Automática

- Processo computacional que verifica se o modelo do sistema satisfaz as propriedades especificadas.
- Explora todos os estados possíveis do sistema (espaço de estados).
- Pode detectar erros que testes manuais não encontrariam.
- Ferramentas populares: SPIN, NuSMV, UPPAAL.

---

### 34.2.4 Counter-examples (Contraexemplos)

- Em caso de falha na verificação, o model checker retorna uma execução que viola a propriedade, chamada contraexemplo.
- Ajuda a entender e corrigir o problema no sistema modelado.
- Essencial no processo iterativo de desenvolvimento e verificação.

---

### Exemplo didático: Modelo simples de máquina de estados com verificação

Imagine um semáforo com estados {Verde, Amarelo, Vermelho} e a propriedade: "O semáforo nunca fica Verde e Vermelho simultaneamente".

- Modelamos estados e transições.
- Verificamos que a propriedade sempre se mantém.
- Caso contrário, o model checker entregaria um caminho (contraexemplo) mostrando uma transição inválida.

---

### Exercícios Comentados

1. Modele uma máquina de estados simples para controle de elevador.

3. Utilize ferramenta de model checking para verificar propriedades em sistemas pequenos.
4. Analise contraexemplos fornecidos e proponha correções no modelo.

## 34.3 Proof Assistants

---

### 34.3.1 Coq Básico

- Coq é um assistente de prova interativo baseado no cálculo de construções indutivas.
- Permite definir funções, tipos e provar propriedades matemáticas e programas.
- Os usuários escrevem lemas (teoremas) e desenvolvem provas interativas usando táticas.
- Exemplo simples: prova que soma é comutativa.

```bash
Theorem plus_comm : forall a b : nat, a + b = b + a.
Proof.
  intros a b.
  induction a.
  - simpl. rewrite <- plus_n_O. reflexivity.
  - simpl. rewrite IHa. reflexivity.
Qed.
```

---

### 34.3.2 Lean Básico

- Lean é outro popular assistente de prova que combina lógica dependente e programação funcional.
- Interface amigável e uso crescente em pesquisa matemática e formalização de teoremas.
- Exemplo: definição e prova básica semelhante ao Coq, mas com sintaxe diferente.

---

### 34.3.3 Provas Construtivas

- No contexto dos proof assistants, provas são construídas explicitamente como objetos computacionais.
- Provas construtivas garantem a existência de objetos com as propriedades demonstradas.
- Diferem de provas clássicas que podem usar argumentos por contradição.

---

### 34.3.4 Curry-Howard Correspondence

- Estabelece uma isomorfismo entre lógica e teoria dos tipos.
- Provas são vistos como programas e teoremas como tipos.
- Permite que provar um teorema seja equivalente a construir um programa que tem certo tipo.
- Fundamento teórico para proof assistants como Coq e Lean.

---

### Exercício Guiado: Prova simples em Coq

Provar que zero é o elemento neutro da adição:

```bash
Theorem zero_neutro : forall n : nat, 0 + n = n.
Proof.
  intros n.
  simpl.
  reflexivity.
Qed.
```

## 34.4 Testing Baseado em Propriedades

---

### 34.4.1 QuickCheck e Property Testing

- Técnica de teste que verifica propriedades gerais de funções, não apenas casos específicos.
- QuickCheck é uma biblioteca que gera automaticamente muitos dados de teste aleatórios para validar propriedades.
- Em vez de escrever casos fixos, o programador descreve propriedades esperadas que a função deve satisfazer.
- Encontra contraexemplos que quebram a propriedade mostrando bugs potenciais.

---

### 34.4.2 Geradores Automáticos

- QuickCheck usa geradores automáticos para criar dados de entrada variados para testes.
- Geradores podem ser personalizados para tipos complexos.
- Aumentam a cobertura de testes explorando diversos cenários.

---

### 34.4.3 Shrinking de Casos de Teste

- Quando QuickCheck encontra uma falha, tenta reduzir o caso de teste ao menor exemplo que ainda provoca o erro.
- Facilita diagnóstico e correção rápida dos bugs.

---

### 34.4.4 Especificação Formal

- As propriedades são expressas formalmente como invariantes, relações ou leis matemáticas.
- Permite um entendimento claro e conciso do comportamento esperado do sistema.
- Facilita integração com técnicas formais de verificação.

---

### Exemplo Guiado: Teste de propriedade em Haskell com QuickCheck

```haskell
import Test.QuickCheck

*-- Propriedade: ordenar não altera tamanho da lista*
prop_length xs = length (qsort xs) == length xs
  where
    qsort [] = []
    qsort (x:xs) = qsort [y | y <- xs, y <= x] ++ [x] ++ qsort [y | y <- xs, y > x]

main :: IO ()
main = quickCheck prop_length
```
